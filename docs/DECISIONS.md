# Принятые решения и ограничения

## Что было в исходном файле

Вложенный заказчиком YML (снимок от 2026-11-06) содержит 13 180 `<offer>`.
Предложения обычно содержат `name`, `typePrefix`, `vendor`, `vendorCode`, `url`, `price`,
`param` с артикулом и кодом товара; последняя запись вложения неполная.
**Нет** `<description>` или детальных
измерительных спецификаций. Нельзя превращать артикул или цену в измерительный
параметр и нельзя декодировать модель по догадке.

Выбраны offer **54170** (ОВЕН ТХ01-224.Щ2.Р-RS) и **54413** (ОВЕН УКТ38-Щ4.ТПП).
Факты дополнены **вручную**, до обращения к LLM, из страниц конкретных товарных
семейств и технического описания на сайте поставщика. Это **подготовка входа**,
а не скрытое обогащение уже при генерации. Спецификации необходимо перепроверять
по паспорту конкретной модификации перед реальной публикацией.

Соответствие входных параметров источникам и ограничения по модификациям
описаны в [`SOURCES.md`](SOURCES.md).

## Основная идея

1. Pydantic проверяет входной JSON и нормализует пустые значения.
2. Python копирует технические параметры **из входа без участия LLM**.
3. LLM получает JSON продукта и отвечает по строгой JSON Schema только
   четырьмя редакторскими полями.
4. Python проверяет `seo_title` (≤70 символов), `seo_description` (800–1200),
   уникальность и число ключевых запросов (3–5), наличие названия модели в
   заголовке. Отдельные проверки сверяют числовые и технические значения с
   входом, включая единицы измерения и обозначения IP, а также ограничивают
   утверждения об отсутствующих параметрах и рискованные термины
   (например, Bluetooth, Modbus, RS-485, Wi-Fi, гарантия, сертификация).
5. Одна попытка автоматического исправления ответа. Если снова не проходит
   проверку — HTTP 502; такой ответ не возвращается как готовый черновик.
6. Пропущенные `expected_specs` выводятся как `данных нет` и попадают в
   `missing_fields`. У генератора отсутствует возможность добавлять технические
   параметры в таблицу карточки.
7. Если есть менее четырёх подтверждённых характеристик и описание короче 100 символов, ответ — `needs_data`, без искусственного текста
   на 800–1200 символов.

## Почему не RAG, база, OCR или агентный фреймворк

Два товара, фиксированный формат результата, нет задач поиска по базе;
все дополнительные механизмы усложнили бы прототип без полезного эффекта.

## Промпт

`app/prompts.py` содержит системную политику точности, игнорирование инструкций
в полях товара, запрет неподтверждённых обещаний и формат результата.
Отдельный пользовательский промпт сериализует факты в JSON. Встроенная проверка
в Python не доверяет одной инструкции «не выдумывай».

## Выбор модели

По умолчанию используется Ollama с моделью `qwen3.5:9b`. Запрос идёт через
native `/api/chat`: схема передаётся в `format`, режим рассуждений отключён
через `think: false`. API-ключ не нужен. Модель может работать на отдельной
машине; приложению нужен доступ к её HTTP API, например через SSH-туннель.

Для облачного провайдера предусмотрен адаптер OpenAI Chat Completions
с `response_format: json_schema, strict: true`. Провайдер выбирается
переменной `LLM_PROVIDER`; технические проверки общие для обоих вариантов.

## Ограничения

- Проверки технических значений, единиц, отсутствующих параметров и рискованных
  терминов улавливают часть ошибок. Это не полная смысловая проверка: возможны
  неверные связи между известными фактами, необоснованные выводы и новые
  утверждения, написанные словами. Сам входной JSON также может быть ошибочным.
- JSON Schema ограничивает форму ответа, а **не истинность утверждений**;
  ответ дополнительно валидируется Pydantic независимо от провайдера.
- Семантический fact-check, поиск в паспортах и source-span citations —
  задача следующей итерации. Нужна проверка человеком.
- Нужны модель и версия провайдера, поддерживающие структурированный вывод.
  Для другого API может понадобиться отдельный адаптер.
- Локальная модель требует памяти и вычислительных ресурсов на машине,
  где запущена Ollama. Скорость зависит от оборудования и выбранной модели.
- В текущем MVP нет автоматического импорта YML, базы, CMS, аккаунтов,
  доступа по ролям и деплоя — согласно ограничениям задания.
- Разные версии руководства или каталога могут содержать отличающиеся значения;
  MVP не разрешает такие расхождения автоматически.
- Веб-интерфейс локальный и не предназначен для внешнего публичного доступа.

## Что улучшить дальше

Машиночитаемые ссылки на фрагменты паспорта для каждой характеристики,
парсер YML/PDF с проверкой модификации, семантический аудит утверждений,
версионирование источников, согласование карточек контент-менеджером,
пакетный веб-интерфейс и сохранение в CMS. CLI уже поддерживает массив товаров.

## Статус демонстрационных результатов

Файлы `examples/outputs/*.json` и `.md` — **ручные редакторские образцы**,
показывающие формат результата на подготовленных входных данных. Они не являются
ответами LLM API. Скрипт `scripts/live_smoke.py` сохраняет реальные результаты
отдельно в `output/live/`. Автотесты используют подменённый HTTP transport.

## Проверка интеграции и публикация

Команда `python scripts/live_smoke.py` обрабатывает два товара через реальный API
после настройки `.env`. Число HTTP-обращений может быть больше двух из-за повторных
попыток. Статус последней проверки и границы автоматической валидации описаны
в [`VERIFICATION.md`](VERIFICATION.md). Для публикации нового репозитория есть
`scripts/publish_github.sh`; ему требуется авторизация GitHub CLI.
